# 実装レビュー

## 対象と結論

対象は、ほうにゃんスタンプ台帳の保存、読み込み、バックアップ、復元に関わる今回の変更である。画面の見た目や、押印・ミッション・交換の意味は変更せず、保存に失敗したときに画面だけが成功したように見える問題を優先して直した。

今回の最優先課題は完了と判断する。主データの書き込みに成功するまで、業務状態、成功表示、報酬、音声、演出を確定しない保存境界を設けた。読み込み前の保護に失敗した置き換えは中止し、読み込みに失敗した起動時も、保護済みの原本が確認できる場合だけ復旧を受け付ける。

## 変更前の最重要問題

変更前の監査では、次の問題を確認した。

- `persist()`が`false`を返しても、押印一括処理、景品交換、取消、ミッションの進行・報酬、児童、クラス、カレンダー、設定などの呼び出し側が無視する経路があった。そのため、保存に失敗しても、画面上では報酬や成功表示が残り、再読み込みで消える可能性があった。
- `importData()`が無関係なJSONや不完全なルートを受け取り、`normalizeState()`の結果として空の台帳に近づける危険があった。
- `restoreAutoBackup()`とJSON置き換えの前に作る保護用バックアップが失敗しても、失敗を明示せず置き換えへ進む経路があった。
- 画像データを含む全状態を最大6件保存するため、`localStorage`の容量を圧迫しやすかった。

## 今回の実装

### 保存境界

`storage-service.js`を追加し、JSONの解析・書き出し、保存領域への読み書き、候補状態の検証、正規化、主データ保存、自動バックアップを分離した。`index.html`ではこのファイルを`calendar-service.js`と`app.js`より先に読み込む。

- 主キー`hounyan-stamp-ledger-v1`は維持した。
- これまでのルート状態JSONを読み込めるようにし、新しい書き出しだけ`format`、`schemaVersion`、`state`を持つ形式にした。
- 状態は候補を複製してから検証・正規化する。主データの書き込みに失敗した場合は、保存済みスナップショットと保存領域を変更しない。
- 有限でない数値、文字列になった`ticketBalance`、負の残高、重複ID、配列内の`null`、必須配列の欠落、画面表示を壊す日時の欠落を拒否する。
- 履歴から参照される削除済みミッションひな形、設定、景品、クラス、選択状態は、正規化で安全に扱える限り読み込みを拒否しない。現行設定のスタンプセットと時間割の教科参照だけは、壊れた状態を新たに保存しないため検証する。
- 保存領域が使えない起動では安全な初期表示を行い、保存を停止したことを画面へ出す。

### 業務操作との接続

主データを書き込めた後だけ、メモリ上の状態、成功表示、フォームの消去、報酬、音声、演出を更新する境界にそろえた。失敗時は`committedStateSnapshot`へ戻して画面も再描画する。

- 最大100個の押印、押印に伴うミッション進行、チケット、スタンプ報酬を一つの主データ保存として扱う。
- ミッション完了・取消、景品購入・購入取消、所有スタンプ、児童、クラス、時間割、カレンダー、設定の失敗時に、メモリだけが先へ進まないようにした。
- `renderDailyMissions()`から保存を伴う生成・評価・報酬付与を外し、表示の再実行で報酬が二重に付かないようにした。
- スタンプ単体とスタンプセットの削除は、削除前の強制バックアップに成功した場合だけ進める。セット内のスタンプ単体削除は拒否し、セット参照を孤立させない。
- `before-import`、`before-restore`、`before-delete`の保護用バックアップは、後続の3分まとめ保存で上書きしない。削除済み画像の整理でも、保護用原本は書き換えない。

### 置き換えと復元

JSONの内容を検証し、正規化した候補を作り、先生の確認を取り、現在の状態を保護してから主データへ書き込む。確認取消、読み込みエラー、検証失敗、保護用バックアップ失敗、主データ書き込み失敗のいずれでも現在の状態を維持する。

起動時の読み込みに失敗した場合も、保存領域が利用でき、壊れた主データの原本を保護できた場合は、有効なJSONによる復旧を許可する。保護に失敗した場合や保存領域自体が使えない場合は、置き換えを停止する。保護用キーに既存の原本があるときは新しい原本で上書きしない。

## 現在の機能と意味

現時点で実装されている主な機能は、スタンプ最大100個の一括押印、20個で1シートとなる仕組み、購入専用スタンプの所有確認、ショップ、スタンプセット、図鑑、ほうにゃん20段階、手動・自動の日次ミッション、テスト児童、チケット、通常学級と特支学級の二重所属、年度と表示絞り込み、カレンダー、日別上書き、時間割、タイマー、JSON書き出し、自動バックアップである。

自動ミッションのうち、現在の自動判定に接続しているのは通常のスタンプイベントだけである。`automaticMissionBaseValue()`は、現状では通常のスタンプイベントを`print_completed_count`と`stamp_earned_count`の両方の基準値として扱う。`question_answered_count`、`correct_answer_count`、`consecutive_correct_count`、`study_minutes`は、問題回答や学習開始・終了の記録と接続していないため自動基準値が0になる。タイマーの経過だけを学習実績とはみなしていない。画面上で自動連携済みの条件と先生が調整する条件を区別することは次の課題である。

## リポジトリ全体の監査結果

### P1 ミッションの学習記録連携

`automaticMissionBaseValue()`の基準値が、実際には押印記録に偏っている。質問、正答、連続正答、学習時間の記録契約がないため、設定画面で期待される条件と自動判定の実体が一致していない。タイマーも学習イベントを確定する仕組みではない。

### P1 時間割の年度・期間管理

`timetableForEditor()`は常に最新の有効時間割を返し、`saveTimetable()`はそれを更新する。年度や有効期間の異なる時間割を追加して選ぶ画面がないため、過去の設定を残したまま次の期間を編集できず、既存の設定を上書きする。重なる期間をどう扱うかも未定義である。

### P2 例外日と所属状態

- 短縮授業の設定が`getDayTimetable()`の時間数に反映されず、短縮後の時間割にならない。
- 予定に保存した開始・終了時刻が現在の表示に出ない。
- 無効化したクラスが新規所属の選択肢に残り、所属登録側でも有効クラスか確認していない経路がある。
- 将来この経路を直す場合も、過去の所属履歴は削除せず、当時の記録として残す。

### 構造上の制限

- `app.js`は約7,000行で、状態の正規化、業務処理、表示、保存がグローバルな処理として混在している。
- `renderDailyMissions()`のように表示処理から状態へ影響しやすい箇所があり、スタンプ履歴の繰り返し走査もある。
- 状態の版管理と移行処理は限定的である。
- `localStorage`への同期保存と画像の文字列化に容量限界がある。
- 複数タブを同時編集したときの競合保護はない。
- `IndexedDB`への画像分離、保存履歴の移行、複数端末との同期、競合解決は未実装である。

### 監査時に見つかった文書・検証の不整合

- 変更前の`README.md`には「ミッション画面は未実装」と読める記述があったが、現在は管理画面、児童別設定、日次表示があるため修正した。
- 手動PDF作成用の元ファイルは未追跡であり、今回の対象に含めていない。
- 変更前には、このアプリ専用の追跡済みテスト一式がなかった。今回`node:test`によるテストを追加した。
- 変更前にTerra Highが確認した`node --check app.js`、`node --check calendar-service.js`、固定50件の画像参照確認は、実ブラウザの表示、実際の`localStorage`容量、ファイル読み込み、印刷を保証するものではない。

## 優先順位と完了条件

### P0 保存と復旧の安全性

成果物は、候補状態を検証してから主データへ書き込み、失敗時にメモリと画面を戻す保存境界、読み込み前の保護、壊れた起動状態からの復旧導線、失敗を独立表示する自動バックアップ、Nodeの回帰テストである。これは今回実装した。

完了条件は、保存失敗で主キーが変わらず、メモリの報酬・チケット・所有状態も戻ること、最大100個の押印とミッション報酬が一度だけ確定すること、置き換え前バックアップ失敗を必ず中止すること、正しい旧形式JSONを失わずに読み込めること、無効JSONや不正な数値を空状態へ黙って落とさないこと、保護用原本が後続保存で上書きされないこと、専用テストが全件成功することである。

### P1 ミッションの学習イベント契約

成果物は、押印、プリント完了、問題回答、正答、連続正答、学習時間をそれぞれどの操作で記録するかを定義した学習イベント契約、自動連携済みか先生入力かを表示で区別する改修、判定の回帰テストである。

完了条件は、各条件の基準値が実際の記録だけから計算され、同じ押印を二重計上せず、タイマーだけで学習実績を水増しせず、未接続の条件を自動達成と誤表示しないこと。既存の手動調整と過去の日次履歴を壊さないテストも必要である。

### P1 年度・有効期間付き時間割

成果物は、年度や開始日・終了日を持つ時間割を複数保存し、対象を追加・選択・編集できる画面、期間の重なりを扱う規則、過去の時間割を保持する移行処理である。

完了条件は、保存した古い時間割が新しい保存で上書きされず、対象日には規則に従う一つの時間割が選ばれ、重複期間・境界日・クラス削除後の表示がテストされ、既存データを読み込んでも履歴を消さないことである。

### P2 例外日と無効クラスの所属

成果物は、短縮授業で表示時間数を切り替える処理、予定の時刻表示、新規所属では有効なクラスだけを選べる表示と保存時検証である。

完了条件は、通常日・短縮日・休校日で時間割表示が一致し、保存した予定時刻が表示され、無効クラスを新規所属へ登録できず、既存の無効化済み所属や過去年度の履歴は残ることである。

### P3 保存方式と性能の拡張

成果物は、状態の版管理と移行手順、画像を状態本体から分離する保存方式、容量超過時の利用者向け回復手順、複数タブの競合検出である。

完了条件は、旧版から新版へ一方向に移行でき、移行前の原本を残し、画像が増えても主状態の容量が予測可能で、同時編集で後勝ちの上書きを起こさず、容量不足・権限拒否・移行失敗を再現するテストがあることである。

### 基盤が信頼できる状態になってから検討する機能

特別ミッション、くじ、チケット消費の新しい仕組み、年度の保管・リセット・名誉段階、児童別時間割上書き、複数端末・クラウド・権限管理、音声自動化、着せ替え交換は延期した。ランキングは教育上の比較と公平性の検討が必要なため、現時点では推奨しない。

これらを進める条件は、P0の保存回帰、P1の学習記録と時間割、P2の例外日・所属、P3の移行と容量試験が完了し、追加機能ごとのデータ移行と復元テストを先に用意できることである。

## Terra Highのレビュー結果

初回レビューでは、次の修正要求があった。

- スタンプ単体を削除したとき、セットの`memberIds`が残って再読み込み時の検証に失敗する可能性がある。
- スタンプやセットの削除前に保護用バックアップが必要である。
- 起動時の読み込み失敗画面が、復旧可能な場合と保存領域が使えない場合を区別していない。
- 時間割の教科参照と、セット購入履歴の`stampSetId`の検証を確認する必要がある。

今回、セット内スタンプの単体削除を拒否し、削除前保護を追加し、復旧可能性を状態として表示し、時間割セルと有効なセット参照を検証した。後続の自動保存による保護バックアップの上書きもテストで固定した。同じTerra High担当による再レビューは承認で、公開を止める重大な追加指摘はなかった。失敗時のメモリ復元、保存状態表示、保護原本の保持、復元後の自動保存による`before-restore`原本の上書き防止も確認済みである。残る確認事項は、実ブラウザの`file://`環境、実容量、実ファイル読み込み、印刷、複数タブ競合である。

### Astraによる実ブラウザ確認（2026年9月5日）

実装後、Playwright CLIの独立したブラウザセッションで確認した。ブラウザ操作ツールが`file://`を許可しないため、検証中だけ`127.0.0.1`の静的HTTPサーバーを使用した。本番の児童データは読み込まず、架空の児童だけを登録した。

- 画面操作からテスト児童を作成し、100個を選択して一括押印。通常スタンプ100個とミッション報酬2個、チケット2枚が保存され、再読み込み後も同じ件数だった。
- ブラウザ内の保存処理に容量不足エラーを注入し、100個の追加が失敗したとき、メモリ状態と保存済みJSONの両方が変更されず、継続表示の警告が出ることを確認した。
- 不正なJSONファイルを`FileReader`経由で読み込み、必須項目のエラーが表示され、既存データが変更されないことを確認した。
- アプリから実際にJSONをダウンロードし、押印を追加してから同じファイルを読み込んだ。置き換え確認後に102個へ復元され、復元直前の103個の記録が`before-import`バックアップに残った。
- 通常学級と特支学級、二重所属の通常児童、基本時間割、予定を既存の保存処理から登録し、再読み込み後も保持された。
- 学校全体の休業日を設定し、通常児童のミッション生成可否が`false`、テスト児童が`true`、当日の授業が空になることを確認した。
- 1440×1000と820×1180で画面を確認し、横方向のはみ出しと表示中の画像欠損がないことを確認した。画像は`output/playwright/storage-0905-desktop-top.png`と`storage-0905-tablet-top.png`に保存した。
- 通常操作でJavaScriptの実行エラーはなかった。初回の`favicon.ico`の404と、意図的に注入した保存失敗は別扱いとした。

Nodeテスト25件と3ファイルの構文検査も親タスクで再実行して成功した。`file://`での実操作、ブラウザの実容量を使い切る試験、画像付きバックアップの容量測定、印刷、複数タブ競合は未検証である。固定画像50件の参照確認は変更前の監査結果であり、今回のNodeテストとは別の確認である。

## 変更範囲と残る制限

今回変更した対象は`README.md`、`app.js`、`index.html`、`styles.css`、`storage-service.js`、`tests`、`docs/IMPLEMENTATION_REVIEW.md`である。`calendar-service.js`の処理は変更していない。親リポジトリの別アプリ、未関係の作業ツリー、既存の`.playwright-cli`、`output`、`tmp`は変更していない。

今回の保存境界は同期型`localStorage`を前提とする。複数タブの競合、画像の別保存、クラウド同期、古い版の大規模な移行、実容量と印刷の確認は残る。ミッションの学習イベント連携、時間割の複数期間、例外日の時間数表示、無効クラスの新規所属制限も、今回の保存安全性を越えるため未実装である。コミット・プッシュ・公開は今回行っていない。
